> 在原有 GUI／DOM 智能体基础上，补充文件与终端操作、领域知识接入、可追溯的执行展示，并优化决策开销与验收证据，使框架开始支持“浏览网页—收集信息—处理文件—交付结果”的完整任务。

本文区分已有能力的改进、新增能力和仍未解决的问题。GitHub 本次更新也包含此前未同步的代码，因此提交中的全部差异不应都归为两天内新增的功能。

## 1. 与原有版本相比，改进了什么

| 方向 | 原有问题 | 本轮改进 | 实际价值 |
| --- | --- | --- | --- |
| 执行能力 | 文件操作依赖桌面点击，容易卡在找文件、改名等环节 | 在 GUI、DOM 之外增加 CLI，支持文件读写、重命名、复制、移动及终端操作 | 网页任务可以继续完成文件整理与交付 |
| 领域知识 | 校园官网、内部系统入口等背景需要反复写进任务 | 增加可编辑的 Markdown 知识库，规划前提供知识，并支持三种筛选方式 | 用户可以持续维护自己的工作环境知识 |
| 执行效率 | 输入与提交可能需要两次决策，存在重复编码和无效重试 | 支持受约束的“输入＋Enter”，优化图片编码、元数据请求和错误重试 | 减少部分任务中的模型调用和等待开销 |
| 结果交付 | 主要展示动作轨迹，分析结果和文件状态不够清楚 | 基于已观察网页生成 Markdown 报告，流式展示内容与来源，并提供文件执行证据 | 支持信息查询、比较分析与文件输出类任务 |
| 调试与监控 | 规划、实际动作、核查和最终结果不易区分 | 重构实时监控与轨迹回看，展示计划版本、动作细节、模型输入输出及核查用途 | 更容易定位失败发生在哪个环节 |
| 跨平台验证 | 平台差异缺少足够的实际验证 | 增加 Mac 运行适配与真实任务测试，整理 Windows 安装更新流程 | 为后续跨平台测试建立基础 |

## 2. 执行机制的改进

### 2.1 三种操作模式协同

| 模式 | 适用场景 | 执行依据 |
| --- | --- | --- |
| DOM | 网页按钮、输入框、链接等可结构化元素 | 当前 AX／DOM 中的元素引用及执行器校验 |
| GUI | 缺乏可用 DOM 的视觉控件、桌面界面 | 截图、视觉定位结果与坐标空间 |
| CLI | 文件读写、复制、移动、改名和终端任务 | 后台命令、退出码、文件元数据及读回结果 |

网页浏览与下载继续通过浏览器界面完成；已有文件的处理可以交给 CLI。CLI 操作结果进入同一条执行与核查链路，不构成绕过验收的捷径。

前端现在按实际定位与执行依据显示模式。例如，视觉定位得到坐标后通过 CDP 点击，仍应显示为 GUI，不能仅因传输通道名包含 `browser_dom` 就显示成 DOM。

### 2.2 规划子任务与实际动作分开

规划描述的是可核查的目标，不要求一个子任务对应一次动作。

例如，“搜索并找到目标论文”可能需要输入、提交、检查结果和更换关键词等多个动作。重新规划时保留旧版本及已发生的动作，不能把旧动作当成尚未执行的步骤。

本轮完善了：

- 重规划的失败证据摘要，包括近期动作、执行反馈和核查结果。
- `strategy_change` 字段，要求说明修订后的策略变化。
- 对原样重复剩余计划、原样重复受阻首步的检查。
- 前端按计划版本收纳历史动作，支持回看当时的计划与现场。

这些约束可以减少明显重复，但不能保证模型换一种说法后就一定采用了有效的新策略。

### 2.3 动作完成与任务完成分开

核查需要区分以下事实：

1. **动作已派发**：执行器收到了点击、按键或命令。
2. **动作产生效果**：页面变化、文件写入、下载完成等效果得到观察。
3. **用户要求满足**：对象、内容、名称、路径和交付范围符合原任务。

本轮加强了下载回执、文件读回正文与文件元数据在核查和报告中的使用。文件写入成功不等于内容正确；下载成功也不等于下载了正确对象。

明确的系统条件继续由代码检查；证据不足或涉及语义的问题交给独立模型核查。Jev 原来已经接入，本轮是完善其使用及展示，并非从零引入 Jev。

## 3. Markdown 知识库与可替换的筛选机制

### 3.1 用户可维护的知识格式

知识使用带 YAML front matter 的 Markdown，保存于独立文件，前端支持编辑、预览和筛选测试。

```markdown
---
id: campus
title: 校园官网
aliases: [学校官网, 校内门户]
keywords: [校园, 通知公告]
url: https://campus.example.org
enabled: true
---

# 适用场景
查询校园通知、报名信息。

## 操作提示
- 通知公告位于首页相应栏目。
- 报名时间和材料要求以通知正文为准。
```

上面的网址仅为格式示例。停用的知识不会进入任何一种筛选方法；测试可以使用未保存草稿，实际任务读取保存后的知识。

### 3.2 三种筛选方式

| 方法 | 行为 | 额外开销 |
| --- | --- | --- |
| 全部提供，当前默认 | 将全部启用知识提供给规划器 | 无额外筛选模型调用，但增加规划输入 |
| 决策模型筛选 | 根据任务返回相关知识 ID，由框架取回原文 | 一次或相应的模型筛选开销 |
| Jev 筛选 | 对知识与任务的相关性进行分类，返回结果和概率 | System One 请求；较大知识库分批处理 |

三种方法通过统一函数接口调度，存储、筛选和规划接入相互解耦。后续可以增加关键词、向量检索或混合方法，而不必重写整个知识库页面和规划器。

一次任务固定知识快照，重规划复用该快照；筛选方法、选中内容、耗时和模型调用可追溯。知识提供背景，不作为任务已经完成的证据。

### 3.3 Jev 的可展示价值

除原有执行核查外，Jev 现在也可用于知识相关性筛选。界面区分操作模式选择、动作后核查、加载就绪、下载等待及整项验收等调用用途，能够查看各次输入、输出和耗时。

需要注意：

- 多个问题可以放在一个 HTTP 请求中，但不等于服务器只进行一次模型前向。
- 接口耗时包含网络、服务排队与处理时间，不等于纯 GPU 推理耗时。
- Jev 的概率不能直接解释为任务真实成功率。

## 4. 性能与执行开销优化

### 4.1 受约束的输入与提交合并

对于符合条件的 DOM 单行输入框，一次决策可以请求输入后按 Enter。执行器仍保留输入和提交两个原始动作的结果，并检查元素、焦点、输入值及可编辑状态等条件。

这不适用于所有输入操作。复杂表单、需要选择联想项的输入、GUI 回退等情况仍需分步处理，不能为减少步数而盲目连按。

### 4.2 减少重复处理

- Jev 同次请求中的图片编码与证据哈希复用相同字节，减少重复编码。
- 对已经观察到的多个官方论文元数据 URL 进行有界并发请求。
- 永久性接口错误不再进行相同的无效重试；临时网络错误仍保留恢复机制。
- 下载与页面就绪仍由框架等待，等待不增加决策步数。

### 4.3 让耗时可解释

本机轨迹列表与详情提供总用时、输入输出 token 和模型调用统计，并区分规划、决策、定位与核查等角色。模型请求、浏览器操作、等待、证据准备和最终验收需要分别观察，不能把所有时间都归为“模型推理”。

本轮没有通过删除必要的 Jev 问题、截图或最终验收来换取速度。

## 5. 前端与结果交付改进

实时监控与历史回看共用三栏工作台：

- **左侧**：规划子任务、实际动作和计划版本，独立滚动。
- **中间**：固定比例的截图区域、动作切换与单行阶段进度。
- **右侧**：执行核查、模型输入、模型输出和任务结果，独立滚动。

具体改进包括：

1. 可以逐个查看动作，切换动作前后截图，并检查实际发送给模型的 DOM 与图片。
2. GUI、DOM、CLI 与框架控制分别标识；显示最终验收的明确结果。
3. 重规划原因通过可展开便签查看，旧动作按计划版本折叠，减少占位。
4. 不因整项验收通过而给缺少独立记录的子任务补造完成状态。
5. 分析结果流式展示；支持 Markdown 标题、列表、代码、表格、引用、分隔线和来源链接。
6. 模型调试统一入口，支持粘贴截图与 Jev 预设调试问题。
7. 知识库及模型配置采用更紧凑的布局，补充切换、展开和折叠动画。

这些改进的主要价值是提高调试效率和结果可解释性，而不只是改变视觉风格。

## 6. 验证结果与数据口径

### 6.1 发布前自动化验证

最新发布副本的定向回归结果为 **225 项通过**，包含浏览器界面、文件操作、下载与验收、规划以及桌面适配相关检查。

这是定向测试结果，不代表全部测试套件没有失败。不同轮次的测试集合存在重叠，不能累加成一个总测试数量。本次尚未完成真实 Windows 桌面的端到端验证。

### 6.2 输入与提交的受控测试

使用真实 Qwen、Jev 与 Chromium，在受控搜索页面进行了两轮各 12 个案例测试。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 通过案例数 | 12 / 12 | 12 / 12 |
| 总决策次数 | 22 | 12 |
| 总运行时间的中位数 | 12.13 秒 | 10.15 秒 |
| 每个案例实际搜索提交次数 | 1 | 1 |

修复后这 12 个案例均由一次决策完成输入与提交，仍保留核查。耗时受远程服务和网络波动影响，以上是限定样本的运行记录，不是普遍性能提升保证，也不是严格的性能基准。

### 6.3 知识筛选的小样本测试

在校园、采购、请假三条草稿知识中，用“查校园通知”任务测试：

- 全部提供方法返回三条启用知识。
- 决策模型与 Jev 均只选中了校园知识。
- 一次完整前端测试中，决策模型约 **1.10 秒**，Jev 约 **0.20 秒**。

这个案例说明筛选流程已经接通并能展示差异，不能据此宣称 Jev 在所有任务上固定快多少倍，也不能证明大规模知识库下的检索质量。

### 6.4 真实 Mac 任务测试

以下为已记录的具体运行，不是整体成功率统计，也不是修改前后的配对性能比较。

| 任务 | 决策次数 | 用时 | 可核实结果与边界 |
| --- | ---: | ---: | --- |
| 指定 RoboClaw 论文下载 | 4 | 约 49 秒 | 核对 arXiv 2603.11558 对应的 PDF 下载回执与实际文件；使用已指定的论文地址，不代表开放搜索已经稳定 |

## 7. 当前不足与下一步

### 当前仍存在的问题

1. **规划器可能加入用户没有要求的条件。** 例如要求 TXT 正文必须含某段标题，或指定使用 TextEdit 打开，造成额外阻塞。
2. **整项验收与子任务状态尚未完全统一。** 某次整项模型判断通过，不等于每个子任务都有独立完成记录。
3. **复杂网站的检索恢复仍有波动。** 明确入口时表现较好，泛化搜索仍可能绕路、重复或忽略已观察内容。
4. **部分系统效果只能确认派发。** 文件打开回执不单独证明窗口已显示，也不能证明用户已经看到了内容。
5. **平台验证尚不完整。** 已进行 Mac 实际任务测试；Windows 仍需要实机验证，尤其是桌面截图、窗口识别、中文输入和文件打开。

### 下一步工作

- 在 Windows 上复测浏览器下载、网页信息整理、文件写入与打开等任务。
- 约束规划器提出的验收条件，区分用户要求、规划建议和可观察证据。
- 改善整体完成判定与执行队列的状态同步，避免“整体通过、子任务未核实”的歧义。
- 加强检索失败后的恢复，利用已观察网页内容，减少回到错误入口的循环。
- 建立固定任务集与重复运行评测，统一统计成功率、耗时、决策次数、token 和失败类型。
- 对知识筛选开展规模化测试，比较全部提供、决策模型和 Jev 的召回、误选与成本。

## 9. 一分钟汇报稿

这两天主要做了三方面改进。第一是扩展任务能力，在原有 GUI 和 DOM 操作之外加入 CLI，让浏览器读取的信息能够进一步保存、整理成文件；同时加入 Markdown 知识库，支持规划前提供领域背景。第二是优化执行和验收，合并符合条件的输入与提交，减少重复处理，并把下载回执、文件读回等系统证据提供给核查器。第三是重构监控与结果交付，让规划、动作、Jev 核查、输入输出和最终报告可以直观回看。发布前 225 项定向回归通过，也进行了论文下载、榜单整理和团队名单保存等 Mac 案例测试。目前主要不足是规划条件可能过度约束，以及整体验收和子任务状态尚未完全统一，下一步重点解决这些问题并开展 Windows 实测。
