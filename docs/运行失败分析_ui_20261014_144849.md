## 三、错误原因（分层）

### 原因 A（主因）：决策模型误判导航状态，重复点击同一入口

第 3 步点击 "Solution Library"（ref 31）后，**代理其实已经进入了方案库页面**：
URL 变成 `#/solution-center`，页面标题 "Solution Library"，并显示 `Total 6756 results`
（方案库共有 6756 条结果）。

但决策模型在第 4～7 步的 `screen_analysis` 里反复写着：

> "已到达**方案中心首页**，点击顶部导航栏的 Solution Library 进入方案库，预期看到文件列表"

模型把「方案中心（Solution Center）」和「方案库（Solution Library）」当成了**两个不同页面**，
误以为自己仍停留在外层首页、需要再点一次才能"进入方案库"。而实际上：

- "Solution Library" 是方案中心页内的一个标签 / 面包屑（AX 里同时存在
  `menuitem "Solution Library"`（ref 36）、`link "Solution Library"`（ref 55）、
  `StaticText "Solution Library"`（ref 65））；
- 第 4～7 步点击的 `ref 55` 是面包屑里的 "Solution Library" 链接，点击它只是对**当前同一页面**
  的一次无副作用重导航，因此 URL、节点数、画面完全不变。

连续 4 次同一动作零进展，命中 `no_progress_limit=4`，触发停滞检测 → 进入重规划。

**证据**（`events.jsonl`）：`route/execution` 事件显示 step 4～7 的点击坐标恒定
`[160.3125, 68]`、`target_ref=55`，`execution.outcome.status` 均为 `executed` 但观察无变化；
`framework_recovery` 事件 `failure_class=step_no_progress`，`failure_key=p0_2`，
`recent_attempts` 记录 4 次 "click Solution Library link"。

### 原因 B：任务理解偏差 —— 在卡片列表里找不存在的 ".ppt" 标识

重规划后，模型（第 8～11 步）认为"当前页面显示多个解决方案卡片，但未见明显 PPT 格式标识"，
于是机械地向下滚动列表寻找带 `.ppt/.pptx` 标识的条目。

但方案库展示的是**解决方案卡片**（方案简介 / 评分 / 评论 / 标签），PPT 文件本身藏在
**每个方案的详情页附件**里，卡片列表上根本没有 `.ppt/.pptx` 后缀标识。模型应当：

1. 点击进入某个方案详情页，再找附件下载；或
2. 使用页面上现成的筛选器（`More Filters`、`Domain/Product Domain`、
   `Synthesis Delivery Scenario`）缩小范围。

而模型两步都没做，只在 6756 条结果里盲目滚动 4 次。滚动走的是视觉定位（`resolved=visual`、
空 target），且 4 次滚动后 AX 节点数始终是 697 不变，说明要么滚动错了容器（内层虚拟滚动列表），
要么根本没有翻出新的可交互内容。第二次连续无进展再次命中停滞检测，而此时
`max_replans=1` 已耗尽，直接以 `stalled` 结束。

### 原因 C：验证条件语言不匹配（规划器缺陷）

规划器给第 2 步（p0_2）写的代码验证谓词是：

```json
{"kind": "text_present", "text": "方案库"}
```

但站点界面是**英文**（"Solution Library" / "Solution Center" / "Total 6756 results"），
中文文本 "方案库" 永远不会出现在 AX 里。因此代码核查对 p0_2 永远返回 `unknown`
（"需要补充观察或独立模型核查"），队列无法推进——规划器没有把用户的**中文目标**
映射到站点的**实际英文界面文字**，导致一个本可确定性核对的步骤（页面已含 "Solution Library"）
始终无法通过。

### 原因 D：规划器重复犯 `download_complete` 谓词错误（被重试自动恢复，但暴露缺陷）

任务"随便下载一个ppt"没有预置 `completion_spec`，系统 `checks` 为空。规划器在
**初始规划**和**重规划**两次都输出了：

```json
{"kind": "download_complete", "check_id": "ppt_download"}   // 初始
{"kind": "download_complete", "check_id": "p0_3"}           // 重规划
```

但 `check_id` 必须引用已有系统条件，空 checks 下引用不存在，校验器两次拒绝：

> `下载谓词 check_id 必须引用已有系统条件`

每次都要重试一次，才把下载步骤改回 `{"kind": "visual"}` 并通过。这说明规划器对
**"无下载验收契约"** 的场景处理不当：系统提示里允许 `download_complete(check_id)`，
但规划器没有意识到本任务没有可引用的 check，直接编造了一个 `check_id`。
（该问题只造成一次规划重试，不直接导致运行失败，但暴露出规划器的鲁棒性缺陷。）

### 原因 E：Jev 核查全程弃权，失去诊断信号

Jev（`d3-flash` 9B）在 step 2～11 对 `settled / correct / next_mode / replan` 四个问题
**全部输出 `unknown`**。其 top 概率普遍只有 0.5～0.84，远低于 0.9 阈值（margin 0.15），
因此全部弃权；只有 step 1 给出了置信判断（`complete / yes / dom / no`）。

在 `review_mode=exclusive` 下，Jev 是唯一语义核查方。它弃权 = 框架**完全失去语义诊断信号**，
既不能确认"已进入方案库"、也不能提示"该重规划"。最终只能靠代码层的
连续无进展计数（`no_progress_limit=4`）兜底触发恢复，而这个兜底又把唯一的一次
重规划机会消耗在了"继续滚列表"上。

### 原因 F：无确定性验收契约（框架固有约束）

`task_analysis` 显示 `kind=generic, contract_status=semantic, check_count=0`，
整个原始任务被列为"未解析要求"。"随便下载一个ppt"没有指定文件名 / URL / 哈希，
框架无法构造可确定性核对的验收条件（`checks=[]`），因此：

- `verification.status = unknown`，`reason = "no deterministic completion contract for this task"`；
- 即使最终走到下载步骤，也只能靠语义核查（Jev）判定，而 Jev 又全程弃权；
- 最终 `reward=null, reward_valid=false`，任务无法被判定为成功。

## 四、错误链总结

```
"随便下载一个ppt"（无验收契约、英文站点）
        │
        ├─(D) 规划器两次编造 download_complete(check_id) → 每次多一次重试
        ├─(C) 规划器写中文 text_present("方案库") → 代码核查永远 unknown
        │
        ▼
第 3 步已进入方案库页面（Total 6756 results）
        │
        ├─(A) 决策模型误判"还在方案中心首页" → 重复点击面包屑 4 次 → 停滞
        │
        ▼
重规划（消耗唯一一次 replan）
        │
        ├─(B) 只在卡片列表滚找 ".ppt" 标识，不进详情、不用筛选 → 4 次滚动无进展 → 再停滞
        │
        ▼
replan 耗尽 → termination_reason = "stalled"
        │
        └─(E/F) Jev 全程弃权 + 无确定性契约 → reward=null，无法验收
```

**一句话结论**：代理其实在第 3 步就已经到达了正确的方案库页面，但由于（A）决策模型
把「方案中心/方案库」误判为两个页面而重复点击、（B）不了解 PPT 藏在方案详情附件里而
盲目滚动，叠加（C）中文验证谓词无法匹配英文站点、（E）Jev 9B 全程弃权、（F）任务本身
没有确定性验收契约，最终在一次重规划被浪费后以 `stalled` 失败。

## 五、改进建议（按优先级）

1. **导航状态识别（针对 A）**：决策模型应结合当前 URL / 面包屑判断"已到达目标页"，
   避免对"已处于目标页面"时继续点击同一导航项。可在决策提示中显式要求
   "若当前 URL / 面包屑已含目标区域，则直接进行下一步，不重复导航"。
2. **附件定位策略（针对 B）**：对"下载某格式文件"类任务，引导模型"先进入详情页，
   再找附件列表"，并优先使用页面筛选器而非盲目滚动。
3. **验证谓词语言对齐（针对 C）**：规划器生成 `text_present` 等谓词时，应使用
   **当前页面观察到的实际文字**（如英文 "Solution Library"），而非用户中文原话。
4. **无契约下载的规划鲁棒性（针对 D）**：规划器在 `checks=[]` 时不应再生成
   `download_complete(check_id)`，应直接降级为 `visual`；或在编译阶段自动把无效
   `download_complete` 谓词归一化为 `visual` 而不是拒绝。
5. **Jev 弃权兜底（针对 E）**：Jev 连续弃权时，可考虑降低阈值到 `top_prob ≥ 0.7`
   仍取 `top_label` 作为弱诊断信号（仅作提示，不冒充确定性奖励），或在该情况下
   更早地触发重规划，避免把宝贵的一次 replan 浪费在机械滚动上。
